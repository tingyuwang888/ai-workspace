**流程对比**

| 阶段 | 一般策略测试 | 带指标策略测试 |
|---|---|---|
| 规则解析 | 判断字段与阈值关系 | 还要解析统计窗口、过滤条件、聚合方式和分组维度 |

| 当前交易 | 直接提交 | 确认“当前笔是否计入指标”后再提交 |
| 结果证据 | 规则命中、函数值、三方字段 | 还要核对实际指标值、阈值、历史贡献和当前笔贡献 |
| 并发执行 | 查询键隔离后可并行 | 共享聚合键或动态群体指标通常必须串行 |
| 重跑 | 更换业务 ID 即可 | 必须使用全新的指标隔离命名空间和时间序列 |

**指标策略额外需要分析**

1. **指标计算方式**

   需要明确是次数、金额、去重数、比例还是动态阈值。例如：

   ```text
   最近1小时同客户失败交易次数 >= 3
   ```

   必须确认事件类型、成功/失败状态、客户分组键、时间精度，以及当前交易是否包含在“3次”中。

2. **历史与当前笔算术**

   每条用例需要分别记录：

   ```text
   历史贡献：2次
   当前笔贡献：1次
   最终预期指标：3次
   规则条件：3 >= 3，预期命中
   ```

   不能只写“构造3笔交易”。

3. **窗口边界**

   通常至少测试：

   - 窗口内
   - 恰好位于边界
   - 刚刚越过边界
   - 被过滤条件排除
   - 当前笔计入或不计入

4. **指标物化**

   历史请求成功不代表指标已经更新。发送当前交易前需要检查平台暴露的事件记录或指标值；若仍为 `0`、`null` 或低于预期，应停止当前用例。

5. **结果分类**

   - 历史未进入指标：`无效用例`或`执行阻塞`
   - 请求成功但目标规则集未执行：`编排阻塞`
   - 指标值正确但目标规则行为错误：`失败`
   - 指标值和规则行为均符合预期：`通过`

**与本次集中度测试的具体区别**

本次集中度策略主要通过客户名或区域码查询 MySQL 快照，函数合并实时/离线金额，然后判断是否超过限额。只要 Fixture 查询键、金额和限额正确，就能执行。

## 🟩 助手

可以，但有一个边界：

**4 个 Skill 已支持含指标策略的完整治理流程；实际执行还要求存在匹配的接口服务契约和执行适配器。** 当前内置的指标接口执行器主要适配收单类接口。其他项目如果没有对应适配器，会完成设计和预览，但在提交前标记为执行阻塞，不会猜测接口。

**职责分工**

| Skill | 指标策略中的职责 |
|---|---|
| `tiance-agent-loop` | 编排完整闭环、环境门禁、Excel 预览、确认和最小重跑 |
| `tiance-testcase-generator` | 解析指标、设计历史事件与当前笔用例 |
| `tiance-policy-test` | 调用接口服务、加载历史、查询指标和采集规则证据 |
| `tiance-report-checker` | 五态分类、根因分析和报告检查 |

**测试流程**

1. **识别执行入口**

   规则包含次数、累计金额、去重数、比例、时间窗口或动态阈值时，自动路由到“指标接口服务链”，不使用 Noah `policyTest` 制造历史数据。

2. **确认四类接口**

   ```text
   历史事件写入接口
   当前笔触发接口
   指标/执行结果查询接口
   调用记录/目标规则证据查询接口
   ```

   四类能力可以由同一个接口提供，但需要分别核实。缺少地址、认证或请求契约时，一次性询问操作人员。

3. **设计指标用例**

   每条规则覆盖：

   - 命中
   - 未命中
   - 阈值边界
   - 时间窗口内外
   - 当前笔计入/不计入
   - AND/OR 各逻辑分支

   用例明确记录：

   ```text
   历史贡献
   当前笔贡献
   最终预期指标
   聚合键
   去重字段
   过滤条件
   时间范围
   预期规则行为
   ```

4. **输出操作人员预览**

   生成 `策略测试报告预览.xlsx`，只包含 `测试明细` Sheet，使用最终报告标准 15 列，用例编号为 `001`、`002` 等。

   操作人员确认前不会写 Fixture 或调用测试接口。

5. **准备隔离数据**

   为每个用例生成新的客户、账户、卡、商户、终端等隔离键。需要数据库 Fixture 时记录插入行 ID，结束后精确清理。

6. **执行历史事件**

   按业务时间顺序调用历史写入接口，保存每次请求、响应、时间和流水号。

7. **验证指标物化**

   历史请求成功不等于指标已生成。通过指标查询接口确认次数、金额、去重数等达到设计值，再发送当前笔。

8. **发送当前笔**

   提交前比较最终序列化请求与设计清单，避免字段被生成器改写。

9. **查询最终证据**

   核对：

   - 实际指标值
   - 平台阈值
   - 当前笔是否计入
   - 目标规则集是否执行
   - 目标规则是否命中
   - 最终决策

10. **五态分类与最小重跑**

   结果只使用：

   ```text
   通过
   失败
   执行阻塞
   编排阻塞
   无效用例
   ```

   只重跑已确认修复影响的用例，不全量重复执行。

**操作人员看到的文件**

- `策略测试报告预览.xlsx`
- `策略测试报告.xlsx`

最终报告沿用预览的 15 列结构，回填实际结果、测试状态、时间和可用的 Noah UUID。接口没有 Noah UUID 时该列留空，接口流水号和 trace ID 保存在实际证据及内部归档中。

**内部归档**

```text
environment-readiness.json
coverage-plan.json
design-manifest.json
design-review.json
testcases.prepared.json
operator-approval.json
fixture-manifest.json
历史/当前请求响应归档
results.json
governed-results.json
analysis.json
rerun-plan.json
loop-trace.json
```
