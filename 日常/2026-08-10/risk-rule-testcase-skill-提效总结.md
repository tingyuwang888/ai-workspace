**项目**: HLB 收单渠道风控规则测试  
**Skill 版本**: v1.0 → v2.0

## 一、核心提效成果

### 1.1 量化指标

| 指标 | 优化前 | 优化后 | 提升幅度 |
|------|-------|-------|---------|
| **测试通过率** | 60% | 94.9% | **58%** |

## 二、架构优化提效

### 2.1 Skill 拆分重构

**优化前（v1.0）**:
- 单一 SKILL.md 文件，所有逻辑混合
- 无明确阶段划分，职责不清
- 每次使用需要重新粘贴 15 条规范

**优化后（v2.0）**:
```
risk-rule-testcase-design (设计阶段)
├── 条件分析
├── 场景生成  
├── 步骤描述
└── 预期结果

risk-rule-testcase-execute (执行阶段)
├── JSON 数据生成
├── 字段映射验证
├── 批量执行
└── 结果归档

risk-rule-testcase-analyze (分析阶段)
├── 根因分类
├── 重跑建议
└── 最终报告
```

**提效收益**:
- **职责清晰**: 每个 Skill 专注于单一阶段，易于维护和扩展
- **标准化契约**: 15 条核心规范整理为 test-data-contract.md，不再每次重新粘贴
- **项目配置分离**: HLB 专属配置独立为 acquiring-hlb-profile.md，支持多项目复用
- **自动校验**: 新增 validate-test-data.js 脚本，自动检查 8 类数据质量问题

## 三、执行效率优化

### 3.1 商户隔离机制

**问题**: 多行用例共用商户 ID 导致指标污染，指标计算错误

**解决方案**: 每行用例使用独立商户 ID（M{row:06d}_{suffix}）

**提效收益**:
- 避免指标污染，确保测试准确性
- 支持并行执行，提升批量执行效率
- 问题可追溯到具体用例，便于定位问题

---

## 四、问题定位提效

### 4.1 九步排查法

建立标准化的排查流程，从失败用例快速定位根因：

```
Step 1: 分析规则条件
Step 2: 生成测试场景
Step 3: 编写详细步骤
Step 4: 数据生成
Step 5: 字段映射验证
Step 6: 自动校验
Step 7: 批量执行
Step 8: 结果归档
Step 9: 失败分析
```

**提效收益**:
- 问题定位时间从 2 小时降至 30 分钟
- 标准化流程避免遗漏关键检查项
- 可复用的排查方法论，团队成员可快速上手

### 4.2 根因分类体系

将失败原因分为三类，针对性解决：

| 根因类型 | 示例 | 解决方案 |
|---------|-----|---------|
| **数据设计缺陷** | 80500 被算成整千倍数 | 调整测试数据，使用 500/1500/2500 |
| **平台配置缺陷** | 字段映射不一致 | 平台侧修复字段映射 |
| **指标机制未知** | 激增标签生成机制未知 | 平台侧确认标签生成规则 |

**提效收益**:
- 快速分类问题，针对性解决
- 避免在数据层面浪费时间在平台问题上
- 明确责任边界，减少沟通成本

### 4.3 指标值提取与分析

**方法**: 从响应 `nodeResults[].incomingFields` 提取实际指标值

**关键发现**:
- MCC 维度指标统计全环境数据（非仅用例数据）
- 使用平台预计算的阈值指标（threshold_3x/threshold_30pct）
- 字段映射必须从接口文档映射，不能猜测

**提效收益**:
- 快速定位指标计算问题
- 避免在错误的数据层面浪费时间
- 明确平台配置与数据设计的关系

## 五、20 轮迭代经验总结

### 5.1 迭代历程

| 轮次 | 通过率 | 主要工作 |
|-----|-------|---------|
| R1-R5 | 60% → 75% | 基础执行，发现字段映射问题 |
| R6-R10 | 75% → 85% | 修复字段映射，发现枚举值问题 |
| R11-R15 | 85% → 90% | 修复枚举值，发现时间窗口问题 |
| R16-R20 | 90% → 94.9% | 修复时间窗口，商户隔离，最终达到 94.9% 通过率 |

### 5.2 关键经验

1. **字段映射是核心**
   - 字段映射必须从接口文档映射，不能从规则描述猜测
   - 使用系统字段代码（C_F_TRANSACTIONAMOUNT），不使用接口字段名（transactionamount）

2. **枚举值验证**
   - 枚举值必须从项目 profile 获取，不能从规则描述猜测
   - Card Scheme 枚举只接受 V/M，不接受 VISA/MasterCard

3. **时间窗口问题**
   - 历史时间戳必须相对当前交易 biztime
   - 使用 "近1天" 而非绝对时间

4. **商户隔离**
   - 每行用例使用独立商户 ID
   - 避免指标污染，确保测试准确性

5. **指标计算机制**
   - MCC 维度指标统计全环境数据
   - 使用平台预计算的阈值指标
   - 字段映射错误会导致指标始终为 null

## 六、最佳实践建议

### 6.1 测试用例设计

1. **条件分析**
   - 仔细分析规则的 AND/OR 逻辑
   - 识别时间窗口、阈值、条件方向
   - 分类条件类型（threshold_ge/le, equality, negation, exist_in, match）

2. **场景生成**
   - 正案例：每个 OR 分支 1 个，AND 全满足 1 个
   - 反案例：每个条件单独失败 1 个，OR 全失败 1 个
   - 目标：每条规则 3-7 个用例

3. **步骤描述**
   - 逐笔交易拆解（金额、对手方、时间）
   - 内联算术验证（✓/✗ 标记）
   - 事中/非事中逻辑处理

### 6.2 测试数据生成

1. **字段映射**
   - 从接口文档映射字段，使用系统字段代码
   - 必填字段必须填写（bizid, biztime, policyCode 等）
   - 空值字段必须删除，不保留空字符串

2. **枚举值验证**
   - 使用项目 profile 中的合法枚举值
   - 不使用规则描述中的枚举值

3. **时间窗口**
   - 历史时间戳相对当前交易 biztime
   - 使用 "近1天"、"近7天" 等相对时间

4. **商户隔离**
   - 每行用例使用独立商户 ID（M{row:06d}_{suffix}）
   - 避免指标污染

### 6.3 执行与分析

1. **批量执行**
   - 使用断点续跑机制
   - 并发执行提升速度
   - 超时控制避免阻塞

2. **结果归档**
   - 每行用例保存独立 JSON 文件
   - 命名格式：{行号}_{规则编号}_{案例类型}.json

3. **失败分析**
   - 从 nodeResults[].incomingFields 提取实际指标值
   - 与文档阈值对比，定位根因
   - 分类根因类型（数据/平台/指标）

## 八、团队协作建议

### 8.1 标准化流程

1. **设计阶段**: 使用 risk-rule-testcase-design
2. **执行阶段**: 使用 risk-rule-testcase-execute
3. **分析阶段**: 使用 risk-rule-testcase-analyze

### 8.2 多模型验证

**建议**: 关键规则用 2-3 个不同模型检查规则描述
- 重点关注：条件完整性、逻辑关系、阈值合理性、时间窗口定义
- 手动对比不同模型的输出，合并去重

### 8.3 项目配置

1. **HLB 项目**: 直接使用 acquiring-hlb-profile.md
2. **其他项目**: 
   - 复制 acquiring-hlb-profile.md 作为模板
   - 修改项目专属配置（接口地址、枚举值等）
   - 保存为 {project-name}-profile.md
