## 盾测「风险态势分析」清理场景 —— 空结果兜底改法（评审稿）

状态：**改法一（查询步 contents[:]）已实测有效但不充分；整链兜底与"按 code 直删"两条路均已实测证伪。** 现有草稿副本：数据 pk=18610（查询001副本）、18626（下线副本）、18627（删除副本），场景 pk=4126，定时任务 pk=595。原件 11259/11264/11265/场景 2872 未动。环境 天策预发(10.56.69.47) 鉴权已恢复，以下结论均为真实发请求取证。

### 一、问题定位（已用 yml + 断言模板取证）

清理场景 2872 的策略链是：查询 001–005（pk 11259–11263，产出 `policyUuid01`–`policyUuid05`）→ 批量下线（pk 11264）→ 批量删除（pk 11265）。

560 报告里级联失败的根因只有一个：查询步用 `data.contents[0].uuid` 提取，当该策略不存在（`contents:[]`）时取 `[0]` 抛 `取[contents[0]]失败`，查询步红 → 后续下线/删除全 `未执行`。

平台侧约束（已核实）：playbook 表单**没有**"失败继续/忽略失败"开关；assert 库**没有**"允许为空"开关。所以兜底只能改 yml 表达式 + 断言取值，不能靠场景配置。

各步断言模板实际取值（取证自 assert_template）：
- 查询 `msgsuccess`：`存在|已存在|成功|已经存在|重复|已激活|无变化` —— 已足够宽松，查询步失败纯粹是提取抛错。
- 批量删除 `deleteMsg`：`成功|不存在|关联引用操作失败|已经被删除` —— **已经容忍"不存在/已经被删除"**。
- 批量下线 `offlinesuccess`：`重复|成功|审核|禁止下线|存在审批的版本` —— **不含"不存在"**，这是删除侧唯一需要补的地方。

### 二、文件级修改清单（改前 → 改后）

| 步 | 原 pk | 位置（yml 路径） | 改前 | 改后 | 必要性 |
|---|---|---|---|---|---|
| 查询001–005 | 11259–11263 | `assert[1].source` | `data.contents[0].uuid` | `data.contents[:].uuid` | 必改：空结果不抛，且让 `policyUuid0N` 被定义为空值（下游占位符才不会"未定义参数"） |
| 批量下线 | 11264 | `assert[0].value` | `"{offlinesuccess}"` | 本地字面量 `重复|成功|审核|禁止下线|存在审批的版本|不存在|已经被删除|无数据` | 必改：下线"不存在的策略"要判绿 |
| 批量删除 | 11265 | `assert[0].value` | `"{deleteMsg}"` | 不改 | 已容忍"不存在/已经被删除"，无需动 |

说明：
- 下线的补集**建议写成本地步（副本内字面量）**，不要去改共享模板 `offlinesuccess`(pk=15) —— 那是全平台多场景复用的，改它会波及别人。若想保留模板化，可另建一个 `offlinesuccessOrNotExist` 新模板供本场景引用。
- 查询步的 `contents[0]→contents[:]` 同时解决两件事：(1) 查询步空结果不再抛；(2) 把 `policyUuid0N` 赋成空值，使 11264/11265 的 `multi.body.uuid: ['{policyUuid01}'…]` 占位符能解析、请求能构造出来。

### 三、实测结果（环境鉴权恢复后，真实发请求取证）

改动一（查询步 `contents[0]→contents[:]`）**已验证有效**：
- 命中空结果时查询步判绿。run `938886`：请求 `code=RISK_TREND_POLICY_ZZZEMPTY2602` 打 `http://10.56.69.47:8088/noahApi/policy/page`，响应 `{"success":true,"code":200,"data":{"total":0,"contents":[]}}`，`output: policyUuid01: []`，`test_result: pass`。不再抛 `取[contents[0]]失败`。

但它**不充分**——`[]` 不被平台当作"已定义变量"：
- 整链 run `595_20260918153011`：查询步绿，**下线步红**，`存在未定义参数: map[policyUuid01:{policyUuid01}]`（请求在拼参阶段就失败，根本没发出），删除步 `未执行`。
- 也就是说，"只把查询步改成 contents[:]"后，整链在无可删数据时**照样失败**，与原始 560（查询步抛错级联）的最终结果一样红。

"按 code 直删"（备选五）**已被证伪**：
- 隔离 run `945190`（18627 副本 single 发 `code` 哨兵、清空 multi、只跑删除步）：请求体 `{"code":"RISK_TREND_POLICY_ZZZEMPTY2602"}` 打 `http://10.56.69.47:8088/noahApi/policy/delete`，响应 `{"success":false,"code":-1,"message":"策略UUID不能为空!","data":null}`。
- 结论：`/policy/delete` **强制要 uuid，不接受 code 作为删除键**。删除接口无法绕开"先查出 uuid"的结构。

### 四、最终判定

在这套"先按 code 查 uuid → 再按 uuid 下线/删除"的结构下，**清理链无法做到"无数据可删时优雅判绿"**，三重硬约束叠加：

1. 平台无条件分支、无空值默认、无场景级"失败继续"（playbook 表单核实无该开关）；
2. 查询步 `contents[:]` 得到的 `[]` 在下游被当作"未定义参数"，请求拼装即失败；
3. 删除/下线接口只认 uuid，不接受 code 直删，无法跳过查询步。

因此本场景不存在"只改 yml 表达式 + 断言"就能兜住空结果的方案。改法一只解决查询步自身，救不了下游。

### 五、后续可选方向（均需另行确认，不在本轮改动内）

1. **治本在上游而非清理步**：560 级联失败的真正病根常是"数据没被成功创建/uuid 没回填"（参见策略生命周期：前置数据准备不幂等、创建步 uuid 未提取回填 → 下游取空）。若保证进入清理时目标策略确实存在且 uuid 已回填，清理链本就能正常删掉，无需为"空结果"兜底。建议把排查重心从"清理步兜底"转向"上游创建/回填是否稳定"。
2. **重构清理结构**：把"查询 uuid"与"按 uuid 删"合并为一个后端按 code 幂等删除的能力（需接口支持按 code 删，当前不支持，属需求侧改动，非测试脚本能解决）。
3. **接受红并降噪**：若"无数据可删"是预期的正常态，可考虑把清理场景从主流程报告中隔离（单独场景/单独任务），不参与主链路通过率统计——属报表口径调整，非脚本兜底。
