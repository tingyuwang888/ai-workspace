# 天策策略测试治理闭环

## 职责与依赖

这是四个天策 skill 的唯一编排入口，不再按报告问题数或通过率自动宣告完成。
先读 [共享治理合同](../tiance-policy-test/references/risk-governance.md)，再读
[通用总规范](../tiance-policy-test/references/metric-pipeline.md)。
本 skill 编排子阶段，不再递归启动通用总编排。通用套负责测试正确性，天策套负责平台适配。

```text
范围与备份 -> 设计/覆盖门禁 -> 平台/执行门禁 -> 天策逐笔执行
    -> 五态复核与证据分析 -> 报告质量检查 -> 完成门禁
                 -> 已确认修复的最小重跑 -> 执行门禁
```

现有 `scripts/orchestrator.py` 的问题数收敛、报告缓存复用和全轮反馈生成逻辑
不满足本合同，不能直接作为治理闭环入口。由当前 Agent 调用下列阶段脚本并执行门禁。
`analyze_feedback.py` 只产出建议，不允许将未经证据复核的反馈直接注入生成器。
旧 orchestrator 仍不可用；治理命令入口见
[可执行治理流程](../tiance-policy-test/references/governance-cli.md)。使用
`governance.py validate-design/classify/validate-rerun` 实施结构化门禁，Agent 保留规则
语义、前置条件及根因确认职责，不将结构校验通过等同于业务语义已验证。

## 1. 范围、触发与备份

完整闭环请求在已授权范围内连续推进，不在每个阶段重复索要同意。仅设计、仅分析、
续查证据或指定子集重跑时，从相应阶段进入，复用身份与输入未变化的有效产物。
业务语义歧义只阻断相关用例及依赖；继续完成独立设计、预检和分析。具备隔离条件且
属于原授权范围的通过子集可以执行，明确其范围并保留全部未完成项，不能声称全覆盖。
若必须等待确认，先准备具体差异、受影响 caseKey、证据与最小决策问题。

先按 [报告交付合同](../tiance-policy-test/references/report-delivery.md) 记录模板与展示偏好。
用户只要求报告描述/样式/标注修订时进入 presentation-only，不运行生成、Fixture 或提交阶段。

- 接收策略编码、落地方案、环境及测试范围；能从授权资料或平台确认的信息自行读取。
  仅对影响语义、范围或外部操作权限的未决事项请求确认。
- 手动请求直接开始；版本变更请求先比较历史记录，再通过天策平台元数据验证实际版本。
  除非用户指定版本，否则使用最新发布版本；版本回退需要确认。
- 修改前复制原始 Excel 和已有运行归档到带时间戳的备份目录并验证文件可读。
  新结果写入新 run 目录；不得覆盖唯一历史证据。
- 固定 `coverage-plan.json`：范围内规则、分支、边界、补充模块、排除项和依据。
  数据不可控只表示缺口，不自动缩小范围。

## 2. 生成与设计门禁

读取 [tiance-testcase-generator](../tiance-testcase-generator/SKILL.md) 和
[通用设计规范](../tiance-policy-test/references/metric-design.md)。

1. 解析落地方案；多策略文件显式传 `--strategy-code` 和匹配的策略配置。
2. 使用现有生成器的 `no-mock` 模式生成候选 JSON/Excel。
3. 按共享合同补齐 `design-manifest.json`，复核每个逻辑分支、边界、预期算术、
   当前笔计入方式、历史事件、前置条件和全部指标隔离维度。
4. 输出 `design-review.json`，仅将门禁通过的用例写入 `testcases.governed.json`。
   `设计待确认` 不提交；部分执行须明确子集并保留原始覆盖缺口。
5. 场景说明与最终数据逐条一致后，重算当前数组数量；保留 `case-lineage.json`，说明
   相较候选及历史报告增加/拆分/移除的原因和覆盖分支，不以旧 summary 决定实际提交数。

保留函数、三方字段、决策路由和预警等级测试；按 assertionKind 使用真实目标断言，
不为非规则用例捏造规则编号。生成器退出码为零不代表设计门禁通过。
参数预检后生成 governance 1.0 设计清单并执行 `validate-design`；将完整最终 params
与清单绑定，边界显式声明 expectedHit，分支用 branchIds 对应冻结的 coveragePlan。

## 3. 平台与执行门禁

读取 [tiance-policy-test](../tiance-policy-test/SKILL.md) 和
[通用执行规范](../tiance-policy-test/references/metric-execute.md)。

- 核对 policyCode/policyVersion/bizType/发布状态；差异必须阻断并确认来源，
  不自动改配置。保留平台快照及时间，已有本地配置不能代替本次校验。
  身份门禁通过后，新请求名称使用本次 `platform.policyName`，归档名称差异；名称缺失
  则阻断。显示名称同步不改变编码/版本，不触发历史记录修改或重跑。
- 调用参数预检后再次对照设计清单。Fixture 按本次 run ID 校验、创建、回查；
  历史事件先于当前事件，确认过滤条件和指标贡献。无法准备的用例记录阻塞。
- 按单笔或明确的 case ID 子集调用现有执行器；使用 `--max-retry 0`，禁止在
  未确认服务器是否已处理时自动重试。证据查询不需要重新提交用例。
- 执行 CLI 必须传 `--design-manifest`。提交前及响应后原子落盘；续跑必须传原
  `--run-id`，完整 case 摘要覆盖参数、断言、目标及 Fixture 合同。已接收请求只补查证据；
  结果损坏或提交结果不确定时阻断，不自动重新提交。
- 准备新数据重跑时使用新身份、新输出文件；保留已通过用例，不全量重跑。

## 4. 五态分类与证据分析

读取 [tiance-report-checker](../tiance-report-checker/SKILL.md) 和
[通用分析规范](../tiance-policy-test/references/metric-analyze.md)。

1. 从本次原始归档复核状态，不相信已有 Excel 的通过标记。
2. 精确定位目标规则集及子策略实例，仅以该目标规则的命中情况判断正反例。
   日志没取到是证据阻塞，不是已经证明目标规则集未执行。
3. 逐层对比设计、生成/预检数据、实际请求、目标节点入参和指标。
4. 运行 `governance.py classify`（平台链）或 `governance.py aggregate-acquiring`（收单链）生成 `governed-results.json`，只使用 `通过/失败/执行阻塞/编排阻塞/无效用例`。
   未提交的计划内用例不能从统计中消失；候选排除项另列覆盖缺口。
5. 生成 `analysis.json`：首个已证实差异、预期/实际值、根因、置信度、证据引用、
   责任归属和下一步。关键词反馈不能充当平台缺陷的证据。
6. 运行现有报告检查器作为质量辅助；固定模板使用 `--audit-only`。
   默认仅展示经复核的严重问题，无严重问题不新增质量检查页。完整质量审计、治理结果、
   根因与缺口保留在 sidecar；按模板兼容位置展示必要结论，不强制增加 Sheet。
   原生执行状态与治理状态分开呈现，最终结论以治理结果为准。

## 5. 反馈与最小重跑

按共享合同形成 `rerun-plan.json`，列明 case ID、已确认原因、修复依据、保留的
测试意图、受影响范围、新隔离身份及审批需求。仅执行已确认数据侧修复或已完成
平台/前置条件变更后的受影响非通过用例。共享依赖变化时显式分析影响范围。
提交前运行 `governance.py validate-rerun`；重生成反馈使用稳定 caseKey，不使用可能变化的 TC 序号。

- `fixParams` 先证明是数据生成问题，不能改变反例本来要验证的条件。
- `adjustExpected` 必须有规则定义依据并显式复核，禁止按实际值反推预期。
- 不明机制只安排经授权的单变量探针，不自动全量试错。
- 修改生产策略、名单、路由或清理存量数据不属于测试授权范围。

## 6. 完成与终止

必须核对规则/分支覆盖、目标证据、五态数量、未完成项说明及备份/归档一致性。
每个非通过项要有证据、置信度、责任归属和下一步；无法确定责任人时明确待分配。
报告区分“分析已交付”“覆盖完整”“全部通过”，三者不能互相替代。

- 严格完成率 = 通过 / 全部计划用例。
- 有效执行通过率 = 通过 / (通过 + 失败)；分母为零显示 N/A。
- 额外报告设计待确认、排除候选、规则及分支覆盖缺口，补充模块单独统计。
- 达到最大轮次（默认 5）、问题数稳定、无自动修复项，仅表示停止，不表示成功。
  尚有缺口时记录 `stopped_incomplete` 或 `needs_confirmation`，附下一步清单。
- 清理只针对本轮验证过的隔离键；原始证据在清理前保存并核对完整。

## 执行方式与交接

当前环境确有 subagent 工具且委派被允许时，优先并行委派独立规则组的设计复核或
只读归档分析；每个子代理明确输入路径、caseKey 范围、输出文件及完成条件。主代理
负责门禁、总量核对和整合。共享策略、Fixture、数据库键或同一工作簿的写入保持单一
所有者；不得把顺序依赖的设计、提交、分析强行并行。否则由本任务顺序执行。
不要新建用户任务代替 subagent，也不要依赖 QoderWork 专有 Task 工具。
脚本路径从本 skill 实际目录解析，相邻 skill 从 `../` 定位，不使用旧
`~/.qoderwork/skills` 硬编码路径。

交接必须带上共享合同路径、相关通用 skill 路径、策略身份、run ID、清单/归档路径、
本阶段门禁及禁止自动修改的边界。摘要只返回五态计数、覆盖缺口、门禁状态、
主要阻塞和产物路径；大块数据留在磁盘上。

每轮保留：coverage-plan、design-manifest、design-review、执行输入与清单、
原始 results、governed-results、analysis、rerun-plan、最终报告及备份位置。

同时维护 `loop-trace.json`：orchestrationMode（agent/CLI）、runId、每轮起止时间、
各阶段状态和证据路径、执行 caseKeys、提交回执数、修复依据、重跑子集及 stopReason。
阶段状态使用 not_started/running/completed/blocked/skipped，跳过必须有原因。
标记完成必须能定位当轮产物，不能事后用几个布尔值推定阶段已执行。
同轮的试跑与剩余批次仍是一轮；只有分析修复后重新执行受影响用例才算新增迭代。
报告重写不增加轮次，旧 orchestrator 未调用时不能声称它执行过。
交付时明确报告“Agent 编排/脚本编排、初始执行轮数、反馈重跑轮数、停止原因”。
首轮通过且无需修复可报告“完成一轮闭环，未触发反馈重跑”，不为表现循环而重复提交。
