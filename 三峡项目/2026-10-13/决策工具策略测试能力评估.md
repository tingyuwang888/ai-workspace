## tiance-policy-test (develop-v3.6.0) 对「决策工具」类组件的策略测试能力评估

评估日期：2026-10-13　环境：重庆三峡融资担保 POC（10.57.80.231，orgCode=sxdb）
评估对象：决策中心 → 决策工具（决策树 TREE* / 决策矩阵 METRIC* / 决策表 TABLE*）

### 一、结论

当前 skill **不能**测试引用了决策工具组件的策略，只能把这类策略当黑盒跑端到端决策。
不是"改造困难"，而是**代码里完全没有决策工具这条路径**：全仓库对 `决策树/决策矩阵/决策表/
bodyguard/modelTool/D_TREE/decisionType(组件义)` 零命中；`.pls` 解码器 `decode_pls.py` 只读
`policyCombineExportData` 和 `scorecardExportDataList`，**不读** `decisionToolExportData`；文档化的
`getAllCompontlog` 节点类型只有 RuleSetServiceNode / FeatureServiceNode / SubPolicyNode /
ExclusiveGateway，没有决策工具节点。

好消息是：扩展**很顺**，因为决策工具的完整定义就躺在 `.pls` 里，且平台已有现成范式可抄——
评分卡链路（`scorecard-pls-testing.md` + `expected_score()`）。

### 二、决策工具在平台里的真实结构（实测取证）

三峡环境已存在专门建的决策工具测试策略：`dt_tree_ref_test`(决策树引用)、
`dt_matrix_ref_ebcp`(决策矩阵引用)、`dt_ref_test`(决策表引用)、`dt_chain_gf2_test`(链式决策表)。

`.pls` 容器 = base64(gzip(JSON))。决策工具挂在顶层键 `decisionToolExportData`（列表），每项字段：

| 字段 | 含义 | 实测样本值 |
|---|---|---|
| `modelType` | 工具类型 | `D_TREE`（矩阵/表应为 D_MATRIX/D_TABLE） |
| `decisionCode` | 工具编码 | `TREE25072515319897650` |
| `source` | 来源 | `HOLMES`（模型工具侧） |
| `version` | 工具版本 | `V4` |
| `content` | 工具本体（JSON 字符串） | `{nodes:[{fieldDetail,nodeName,label,isRoot,x,y,id,shape}], edges:[]}` |
| `inputData`/`outputData` | 输入/输出字段定义（JSON 字符串） | 字段 displayName/dataType/sourceKey 等 |
| `defaultDecisions` | 默认决策（JSON 字符串） | 命中兜底决策 |

决策流里通过节点属性引用工具（在 `policyCombineExportData` 内）：

```json
{"attributes":{"code":"TREE25072515319897650","decisionType":"D_TREE",
 "decisionName":"cai_0725测试_副本","decisionUuid":"TREE25072515319897650","version":4}}
```

即：策略提交身份仍是**外层策略编码**，工具靠 `code + version` 被引用——这与评分卡"身份取
外层 policyCombineExportData[0]、不取组件内层编码"完全同构。

### 三、当前 skill 能做到 / 做不到

能做到：策略整体经 `/noah/policyTest` 提交可跑通（工具节点随流执行），最终决策
`policyDealTypeName`/预警等级可断言；`flowModelinAndOutputParams` 里理论上能看到该节点原始出入参。

做不到：
1. 无法从工具定义生成系统性用例（树路径 / 矩阵单元格 / 表逐行的覆盖，生成器四大模块里没有）。
2. 无法精确断言工具输出（五态判定锚定"目标规则命中"，无工具级 assertionKind）。
3. 预检不适配（`ruleCatalog`/`expectedEvidence.rules` 对工具节点无效，只能落"证据阻塞"）。
4. `.pls` 解码不覆盖 `decisionToolExportData`，无法反推工具配置。

### 四、扩展改造点与工作量

按评分卡链路照搬，分五处，无需改动三链+治理的总体架构：

1. `decode_pls.py`：新增解析 `decisionToolExportData`，把 `content` 的 nodes/edges 解成覆盖模型
   （树=根到叶路径、矩阵=维度×单元格、表=行），并解析 input/output/defaultDecisions。
2. 身份与版本门禁：提交身份用外层策略编码；新增"流内引用 version vs 工具 version"漂移校验
   （类比评分卡身份门禁）。
3. `tiance-testcase-generator`：新增"决策工具覆盖"模块，产出路径/单元格/行用例，预期=工具叶子
   输出字段值 + 最终决策。
4. 证据与判定：新增 assertionKind（如"决策工具输出"），从 `getAllCompontlog` 按工具节点类型提取
   实际输出比对；`governance.py classify` 允许目标证据是工具节点而非规则命中。
5. 策略配置：新增 `decisionToolCatalog` / `decisionToolDependencies`（类比 ruleCatalog/ruleDependencies）。

**唯一仍需一次真实跑笔才能定的点**：D_TREE 节点在运行时 `getAllCompontlog` 里的确切 nodeType
名称与输出字段形态（用于写证据提取器）。本次未能取到，原因有二：(a) 直连 API 被网关反爬请求头
拦截，页面内 fetch 复现不了应用注入的头（应用自身请求 200、我构造的 401）；(b) `.pls` 导出是前端
Blob 下载，被 Chrome 自动化模式拦截。静态定义已从本地样本完整获得。

工作量估计：静态侧（解码+生成+配置+身份/版本门禁）约 1–2 人日（对齐已有评分卡参考规模）；
运行时证据侧（补一次真实跑笔取 nodeType → 映射 + classify 集成 + 报告列）约 1 人日。合计约
**2–4 人日**，属增量扩展，不动主干。
